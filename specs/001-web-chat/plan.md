# 구현 계획 · 로그인과 관리자 승인이 있는 텍스트 챗봇

**Git 브랜치** `codex/rust-restart` · **Spec Kit 기능 식별자** `001-web-chat` · **작성일** 2026-11-21  
**기준 문서** [첫 기능 명세](spec.md)

## Summary

직원이 Google로 로그인하면 자신의 승인 상태가 보인다. 관리자가 사용을 승인한 뒤에는 같은 웹페이지에서 모델과 텍스트 대화를 이어간다. 첫 배포 단위는 로그인에서 실제 답변까지 연결되는 한 개의 Rust 서비스다. 현재 구현은 루프백 헬스체크까지이며 아래 내용은 구현 설계다.

## Technical Context

| 항목 | 구현 결정 |
| --- | --- |
| 실행 환경 | 기존 Rust 1.93 이상, Axum 0.8 및 Tokio 재사용. OCI 시연 대상은 Linux ARM64의 단일 컨테이너 인스턴스 |
| 추가 의존성 | JSON 직렬화에 serde, 비동기 HTTPS와 응답 스트림에 reqwest, Access 서명 검증에 jsonwebtoken, SQLite 비동기 접근·마이그레이션에 SQLx 사용 예정. Rust 1.93 빌드를 확인하고 Cargo.lock에 고정 |
| 브라우저 | 동일 출처 HTML·CSS·JS. 한글 여러 줄 입력, 전송·중지 버튼, 발신자 표시, 생성·종료 상태를 제공한다. 대화 텍스트는 문자 그대로 렌더링한다 |
| 저장·실행 | 기관별 로컬 볼륨의 SQLite. 한 질문당 서버 생성 작업 하나. 시작·종료 상태는 즉시 저장하고 생성 중 텍스트는 짧은 배치로 저장한 후 전달한다 |
| 성능·범위 | 페이지당 열린 대화 하나, 대화당 진행 중인 답변 하나. 느린 응답에서도 완료 전 첫 글을 읽고 중지할 수 있어야 한다. 처리량과 모델 응답 시간 보장은 이 명세에서 정하지 않았다 |
| 검증 환경 | 격리된 서명키·모델 입력으로 오류와 경합을 재현하는 Rust 테스트, 별도 Access 환경에서 실제 Google 계정·실제 모델을 사용한 브라우저 검증, ARM64 Compose 재기동 확인 |

Spec Kit 헌장은 아직 미작성 템플릿이다. 명시된 프로젝트 기준으로 조사 전과 설계 후를 점검했다. 아래 판정은 설계 적합성에 대한 것이다. [작업 기준](../../AGENTS.md) · [인증 기준](../../docs/AUTH.md) · [배포 절차](../../docs/DEPLOYMENT.md)

| 기준 | 조사 전 확인 | 설계 후 판정 |
| --- | --- | --- |
| 로그인·승인·소유권 | Google 전용 Access와 승인 대기를 유지 | 통과. 서명 검증 후 등록, 매 요청 승인 확인, 관리자도 대화 소유권 검사 |
| 실제 응답과 진행 | 루프백 헬스체크가 유일한 현재 기능 | 통과. 제공자 본문·종료 신호에 연결하고 중지·오류를 분리 |
| 기관별 독립 배포 | 인증·모델·저장소는 교체 가능해야 함 | 통과. 신원 검증, 모델 클라이언트, 저장 처리를 웹 경로에서 분리. 브라우저 자산은 기관 내 제공 |
| 이관·시연 경계 | 기존 프로젝트에서는 인증 설정만 이관됨 | 통과. 새 코드와 빈 DB로 시작하고 시연 전 별도 Tunnel·Access 앱에서 검증. 기존 서비스·사용자 데이터 이관 작업 없음 |

## Project Structure

| 예정 경로 | 책임 |
| --- | --- |
| `src/main.rs`, `src/lib.rs` | 설정·서버 조립, 테스트 가능한 라우터, 기존 헬스체크 |
| `src/auth.rs`, `src/accounts.rs` | Access 신원 검증, 계정 등록과 최초 관리자 지정, 승인 상태 전이 |
| `src/chat.rs`, `src/model.rs`, `src/store.rs` | 대화 소유권, 질문 실행과 중지, 모델 응답 해석, DB 읽기·쓰기 |
| `web/`, `migrations/` | 같은 출처의 화면 자산과 버전별 DB 변경. 빌드에 포함 |
| `tests/` | 인증·권한, 중복 전송, 응답 상태와 복구의 통합 검증 |
| `infra/Dockerfile`, `compose*.yaml`, `.dockerignore` | 읽기 전용 루트와 UID 10001 유지. 데이터 디렉터리만 쓰기 허용. 빌드·배포 아카이브에 필요한 자산과 마이그레이션 추가 |

## 구현 순서와 인수 기준

| 순서 | 동작과 의존 관계 | 명세 추적 |
| --- | --- | --- |
| 1. 로그인과 등록 | 서명 검증 → 원자적 계정 등록 → 대기 화면·로그아웃. 재로그인·동시 첫 방문에도 한 계정 유지 | FR-008~010, FR-012 · SC-004~005 |
| 2. 승인 관리 | 지정 관리자만 신청자 목록과 상태 변경 사용. 일반 직원의 관리 접근, 승인 취소 뒤 다음 요청, 관리자에 의한 타인 대화 읽기를 차단 | FR-007, FR-010~011 · SC-004~007 |
| 3. 한 대화의 왕복 | 승인된 소유자의 질문 한 건을 한 번만 접수. 앞선 완료 대화와 함께 실제 모델에 전달하고 답변을 점진적으로 표시 | FR-001~004, FR-007 · SC-001, SC-005 |
| 4. 종료와 검증 | 중지·실패·권한 상실 경합 처리. 이미 받은 글을 유지하고 다음 질문 허용. 별도 환경에서 로그인부터 승인 취소까지 실측 | FR-005~006, FR-011~012 · SC-002~004, SC-006~007 |

설계 근거는 [연구 기록](research.md), 트랜잭션과 상태는 [데이터 모델](data-model.md), 화면·요청·이벤트는 [인터페이스 계약](contracts/web.md)에 정의했다. [검증 절차](quickstart.md)는 구현 후 인수 시 사용한다.
